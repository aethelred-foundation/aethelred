sovereign verification infrastructure, while making the remaining production
requirements explicit and machine-readable.

## Production Blockers

### 1. Hardware Attestation

Current: `docker-attestation.json` uses a Docker demo transcript with a
Nitro-compatible evidence shape.

Production requirement:

- Nitro Enclaves, SGX, SEV-SNP, Intel TDX, or approved sovereign-cloud quote
- verifier that checks quote freshness, measurement, PCR/MRENCLAVE/launch digest
- policy-bound measurement allowlist
- attestation evidence retained in the evidence bundle

### 2. zkML Or Deterministic Verification

Current: `evidence-bundle.json` contains a structured demo zkML transcript.

Production requirement:

- production proof for high-value model steps, or
- deterministic verifier evidence for workflows where full zkML is not practical
- circuit/version/verifying-key registry
- proof verification result bound into the seal

### 3. External Compute Provider Quote Verification

Current: `external-compute-report.json` can normalize Docker, external confidential-compute,
sovereign-cloud, and on-prem proof claims, and it fails closed when provider,
attestation type, region, or hash bindings are invalid.

Production requirement:

- provider-native quote verification for external confidential VM evidence
- sovereign-cloud and on-prem adapters with approved quote parsers
- measurement allowlist and workload identity registry
- provider SLA, support, and incident response terms
- policy for when an upstream compute provider is accepted, quarantined, or rejected

### 4. Governed Key Custody

Current: signers are generated in memory per proof run.

Production requirement:

- KMS/HSM custody for seal, policy, anchor, and auditor keys
- dual-control rotation
- revocation list
- key registry public enough for verifiers
- incident rotation runbook

### 5. Legal Verifier Identities

Current: verifier votes are signed by demo verifier identities.

Production requirement:

- legal entity mapping for every verifier DID
- validator/auditor service terms
- jurisdiction and sector scope
- conflict-of-interest policy
- evidence retention and incident cooperation obligations

### 6. Independent Auditor Countersignature

Current: `auditor-attestation.json` is generated by the public proof path.

Production requirement:

- independent security auditor signature
- regulatory controls review
- scope letter and exceptions
- production claim approval boundary

### 7. Chain Or Permissioned-Zone Anchoring

Current: `anchor-manifest.json` produces a local ledger anchor and a
chain-ready payload.

Production requirement:

- accepted Aethelred testnet transaction, or
- permissioned institutional-zone anchor
- retry and finality policy
- anchor transaction included in the regulator pack

## Exit Criteria For A Regulated Pilot

A regulated pilot should not begin until all of the following are true:

1. `npm run validate` passes.
2. Docker service is healthy.
3. The target scenario returns `valid: true` from `/v1/seals/latest/verify`.
4. The target scenario returns `ledger_valid: true` in `/v1/regulator-pack/latest`.
5. If external compute is used, `/v1/external-compute/latest` returns `accepted: true` with provider-native quote verification enabled.
6. A real deployment environment is selected: sovereign cloud, on-prem, or permissioned zone.
7. Key custody plan is signed off by security owner.
8. Verifier identities are mapped to real organizations or pilot participants.
9. Production claim boundary is approved by legal/compliance owner.
10. Auditor scope is defined.
11. Anchor submission path is operational.

## Why This Matters Strategically

This is how Aethelred avoids competing as a generic verifiable-compute clone.
The differentiated product is not "Docker job with proof." It is an evidence
operating system for regulated AI decisions:

- who requested the decision
- which model ran
- what policy applied
- which upstream compute proof was accepted or rejected
- where processing was allowed
- which verifier quorum accepted the evidence
- who is liable
- what was anchored
- what can be exported to auditors and regulators

That is the path toward sovereign verification infrastructure rather than
another developer-only compute product.
